# 接口需求答复 · 2026-10-26

回复 ChatGPT 转来的「采集与存档交付」需求。按用户确认的**缩小范围**处理：只改进通用的采集与存档能力，独立于 AI、Telegram 和回复系统。

上游发布：**插件 4.3.0**；公共接口 `My0511API` **仍为 1.2**（无变化）；新增**存档数据协议 v1**（`_data/`）。规范以 `docs/存档格式规范.md` 第 7 节为准。

## 一、已实现
| 需求 | 实现 |
|---|---|
| 上游负责用户在界面里选定的采集、翻页和存档更新，下游不重复采集 | 沿用现有采集（帖子页、版块列表、搜索结果、巡查、自动跟进、队列）。下游停用自己的后台采集后，只读 `_data/` |
| 保持 Markdown 兼容，增加机读逐帖文件和版本化清单 | `_data/threads/<tid>.json`、`_data/manifest.json`；Markdown 不变 |
| 清单含帖子 ID、来源标识、版本、相对路径、校验值、采集时间、完整性、失败原因 | `sourceId`、`threads[tid].{revision, seq, mdFile, mdSha256, jsonFile, jsonSha256, capturedAt, writtenAt, complete, capture, lastFailure}` |
| 正文写完才发布就绪版本 | 顺序：Markdown → JSON → 日志 → 清单；每个文件整体替换写入；JSON 写失败清单不前进 |
| 增量读取，处理重启、改名、权限丢失、旧备份恢复 | 全局 `seq` + 日志 `journal/`；`generation` 换代；阅读器按 `(tid, jsonSha256)` 去重；改名在重建时标 `mdMissing`；权限丢失时不发布；旧备份覆盖由浏览器记录的序号高水位识别并换代 |
| 配置全部在上游界面，不加跨扩展命令通道，下游不得写存档目录 | 照此执行；设置页新增「机读存档」（状态、重建） |

## 二、没有实现（不在本次范围）
- 按指定用户名巡查新主题并给回复模块提供触发信号；自动把主题加入回复跟踪；专供自动回复的通知或远程控制通道。用户已撤回这些需求，上游不提供。
- 楼层 pid（`floorId`）：Markdown 里没有保存，协议里为 `null`。如需要，单独提需求，上游可在后续版本补充，并保证向后兼容。
- 采集任务、巡查名单的远程修改：没有命令通道，只能在上游界面操作。

## 三、字段格式与错误处理
见规范第 7.2～7.5 节。要点：
- 时间：论坛字段原样（北京时间到分钟，带精度说明）；插件生成的 `writtenAt`、日志 `at` 为 ISO 8601 UTC。
- 不知道的数据给 `null` 或 `capture:{known:false}`，不猜。
- `complete`：`true` 完整、`false` 增量、`null` 不知道。`lastFailure` 记最近一次失败或跳过的原因，不改 `revision`。
- 机读写入失败时，插件设置页显示最近的错误，清单停在原地。

## 四、配置入口
插件「设置」页：
- 存档文件夹：机读存档只在选了文件夹时生成。
- 机读存档：查看状态（收录数、序号、代、覆盖范围、最近错误），以及「从现有存档重建」。

## 五、迁移与接入（Codex）
1. 用户升级到 4.3.0，在设置页点「从现有存档重建」，等 `coverage` 变成 `full`。
2. 下游实现规范 7.6 的阅读算法：保存 `{sourceId, generation, cursor, 每帖已处理的 jsonSha256}`。首次接入时把现有全部帖子当作「基线」，在下游自己的库里标记为已处理，不产生任何动作。
3. 确认下游读到的内容与上游一致后，再停用下游的采集定时器和入队逻辑。
4. 下游的进度、去重、草稿等存在下游自己的数据库；不写存档文件夹，不读写上游 storage。
5. `complete !== true` 或有 `lastFailure` 的帖子，按「数据不完整」处理。
